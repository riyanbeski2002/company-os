# ESC-009 — Investigate why Claude Code's own sensitive-file permission prompt blocks headless Tier-2 writes under .company/worktrees/<TASK>/ even with --permission-mode acceptEdits

## Context

Hit on VIDEO-LAUNCH-01 (video-editor-01, 2026-10-17): worker self-reported TASK_BLOCKED, 'writes inside worktree assets/launch-video/** are held by a Claude Code sensitive-file permission prompt (path under .company/), /tmp writes are denied by the ownership hook; headless run cannot approve.' Likely cause: Claude Code's built-in sensitive-path heuristic may be treating the whole .company/ tree as sensitive (plausibly because .company/secrets/ lives alongside .company/worktrees/), colliding with Tier-2 worktrees also living under .company/. Workaround applied for this one run per Riyan's explicit instruction: launched with --dangerously-skip-permissions (logged, not silent). Needs real investigation: (a) confirm the actual mechanism Claude Code is applying, (b) decide whether worktrees should move outside .company/ (e.g. a sibling .worktrees/ dir) or whether a settings.json permission rule can allow-list .company/worktrees/** without weakening the sensitive-file protection around .company/secrets/.

## Resolution

Investigated empirically rather than guessing between the two proposed fixes -- both turned out to be wrong, and neither would have fixed the real mechanism. Live-tested against real claude -p invocations with --plugin-dir set (required for --agent, so required for every real Tier-2 launch): (1) Moving the worktree outside .company/ entirely (a sibling .worktrees/ dir) did NOT fix it -- still blocked, same "sensitive file" denial. Rules out the '.company/secrets/ poisons the whole tree' theory outright. (2) A project-scoped .claude/settings.json permissions.allow rule for .company/worktrees/** did NOT fix it either -- Claude Code's sensitive-file protection is not a normal permission gate and ignores the allow list by design. What actually explains every observation: this is Claude Code's per-exact-absolute-path WORKSPACE TRUST, not a sensitive-file-content heuristic at all. A path that was never interactively confirmed via the trust dialog (and has no hasTrustDialogAccepted:true entry in ~/.claude.json) gets every Write/Edit denied in headless mode, project-wide, regardless of which specific subpath -- confirmed by testing fresh, never-trusted clone paths both inside and outside .company/, with and without a settings.json, with and without .company/secrets/ present: all blocked identically. Decisive test: a FRESH worktree created today from the REAL, already-trusted /Users/User/dev/company-os (hasTrustDialogAccepted:true, confirmed in ~/.claude.json) correctly inherited that trust and wrote to assets/launch-video/*.mp4 -- the exact path and shape from the original VIDEO-LAUNCH-01 incident -- with zero permission denials, via both the Write tool and Bash. Trust DOES correctly extend from an already-trusted --plugin-dir root to any worktree created under it; this is not a structural company-os defect. Conclusion: the original incident could not be reproduced against the current environment. Most likely a transient issue (the trust record showed lastVersionBase 2.1.301 for the real repo; this machine now runs 2.1.302/2.1.303 -- a point-release difference consistent with something that shifted since). No structural fix applied because none was needed -- worker.py's existing skip_permissions escape hatch (ESC-009's original workaround) remains available if this ever recurs, and if it does, capture the exact Claude Code version and ~/.claude.json trust state at the time, since that is what this investigation could not retroactively recover.
