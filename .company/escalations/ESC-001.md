# ESC-001 — Decide whether company-os keeps hand-rolling worker parallelism/concurrency (worker.py, slots.py) or adopts Claude Code's native 'Agent Teams' (team lead + shared task list + parallel teammates) for that layer, and confines custom code to the governance layer (evidence rule, baseline, risk gates, advisors) that Agent Teams does not provide.

- **Status**: open  ⛔ blocking
- **Kind**: decision
- **Raised by**: company-pm at 2026-08-16T18:01:44Z

## Context

NORTH_STAR.md's own 'what we will not build' section says: 'A second orchestration platform. Verify the native primitive first. Most of what a custom framework would provide, Claude Code already does.' That principle has not yet been checked against current reality. Claude Code now ships a built-in multi-agent orchestrator ('Agent Teams' — a team-lead session coordinating parallel teammates via a shared task list) as of 2026, still experimental/off by default. company-os's worker.py/slots.py/taskstate.py duplicate a meaningful slice of that: spawning workers, tracking concurrency slots, detecting a busy task. The two verified bugs I just filed (runaway concurrent baseline processes; a check-then-act race that lets one task be built twice) both live in exactly this hand-rolled plumbing, not in the governance layer that is company-os's actual differentiator. config/capability-registry.yaml has no entry evaluating Agent Teams — it has never been checked.

## Options

1. Evaluate Agent Teams now (small spike): if it can host the parallel-worker mechanics reliably, migrate worker launching/concurrency onto it and delete the equivalent hand-rolled locking/slot code, keeping company-os focused on evidence/baseline/risk-gates/advisors — the part nothing else provides.
2. Stay on the custom worker layer for now (Agent Teams is experimental and off-by-default; migrating a working-if-buggy system onto an unstable primitive is itself a risk), but fix the two concurrency bugs properly and revisit Agent Teams once it graduates from experimental.
